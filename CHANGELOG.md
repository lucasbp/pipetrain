# Changelog

## Unreleased

- Parallel `merge --apply` now knows which deploys compete for the same resource. For each repo, the workflows expected on push (and the ones chained to them) are read at the base branch, reusable workflows included, from the same repo or from another one (`org/repo/.github/workflows/x.yml@ref`), through the API and the same cache. A shared self-hosted runner label (`runs-on`), a runner group and a concurrency group become resources: deploys that need the same resource run one at a time, in queue order, while other repos keep going up to `max_parallel`. GitHub-hosted runners (`ubuntu-*`, `windows-*`, `macos-*`) are not resources. A `runs-on`, label, group or reusable reference that cannot be resolved (`${{ }}`, unreadable file, unreadable repo) becomes the shared resource `dynamic`, so when in doubt it is serial. A concurrency group is scoped to its repository on GitHub, so the key is `(repo, group)` and the same name in two repos does not serialize. `merge.deploy_slots` (`"<label, group or dynamic>" = N`, default 1) raises the limit per resource. `plan --json` gains `deploy_resources` (repo to resource ids, omitted when empty, additive, schema stays `1`). See [docs/merge.md](docs/merge.md#deploy-resources).
- A deploy whose expected run is `queued` (no run of the set started yet) no longer consumes `merge.timeout_minutes`: the clock stops while it waits, the step shows `waiting for a runner` and the `max_parallel` slot goes to another repo that does not need the same resource. The wait has its own ceiling, `merge.queued_timeout_minutes` (default `180`, summed over the whole wait): past it the step stops with `deploy still queued for a runner` and the next run resumes it.
- `merge --apply` asks every DDL and infra gate at the start, before any merge. With more than one gate it lists them (`repo#n`, type and the file that triggered it) and asks once for all; if that is not confirmed it asks about each one. A confirmed gate PR is queued like any other and runs in parallel with the PRs that do not depend on it, and its pause no longer blocks the queue. A gate that is refused, unanswered or asked without a terminal holds only its own branch: the PRs that depend on it (any plan edge, or the same repo and base) are skipped with `stopped after an earlier failure`, the pause step is `stopped`, the exit code is 5, and every other PR keeps merging. `--gates-confirmed` still answers everything and nothing is confirmed implicitly. The dry run lists the gates it would ask (`notices` in `--json`, the compact preview) and asks nothing. Package waits keep their own confirmation. See [docs/merge.md](docs/merge.md#confirmation-and-gates).
